# Preserve hand-maintained files across Fern regeneration with `.fernignore`

- **Date:** 2026-08-25
- **Status:** Accepted

> This record was written on 2026-08-25 from the repository's commit history and
> current file contents. It documents a decision that was already made and is
> already in effect — it is a reconstruction, not a contemporaneous record. The
> rationale below is quoted or paraphrased from commit messages where possible;
> where it is inferred from the code, that is stated.

## Context

Nearly all of `src/` in this repository — 782 TypeScript files — is generated by
`fernapi/fern-typescript-node-sdk` from an API definition that lives in a
different repository (`.fern/metadata.json`, `originGitCommit`
`4e878a3cc88c52d6d6165f6e4ad46bb26dafec60`). Regenerations land as
`SDK regeneration` pull requests authored by `fern-api[bot]` — there are five in
the first ~17 commits of this repo's history (`e981390`, `8305147`, `763f884`,
`b70bcab`, `10273b3`, `af01440`, `6a6644b`).

But the repo is not purely generated output. It also has to carry things the
generator knows nothing about and would clobber:

- Contentful's release path — `RELEASING.md` and
  `.github/workflows/publish.yml`, which publish to GitHub Packages using a
  Vault role provisioned by `.contentful/vault-secrets.yaml` (`4050417`,
  `ba19aae`)
- legal artifacts and their generator — `LICENSE`, `NOTICE`, `licenses/`,
  `AUTOMATION-FOR-LICENSES.md`, `scripts/update-licenses.js`
- Contentful org plumbing — `catalog-info.yaml` for Backstage (`b767586`),
  `.github/CODEOWNERS` (`ccb0c95`), issue and PR templates (`e4b4f72`)
- hand-written contributor documentation — `CONTRIBUTING.md`, `BUILDING.md`
  (`d795327`)

Without a mechanism to hold those, every regeneration would either delete them
or revert them to generator defaults.

## Decision

Maintain an explicit allowlist of hand-maintained paths in `.fernignore`, and
require that any new hand-maintained file be added to it in the same change.

`b767586` ("chore: add LICENSE + protect manual files via .fernignore
[DX-1109]") is where this became the deliberate policy rather than an incidental
detail. That commit added seven paths to `.fernignore` and stated the reasoning
directly:

> Add CONTRIBUTING.md and LICENSE to .fernignore so the manual edits survive
> future SDK regenerations.

and, for the second batch:

> Extend .fernignore to cover the new manual files

The allowlist has grown with each hand-maintained addition since — e.g.
`.github/ISSUE_TEMPLATE` and `.github/pull_request_template.md` with `e4b4f72`,
`BUILDING.md` with `d795327`.

The corollary, made explicit in the `CONTRIBUTING.md` and
`.github/pull_request_template.md` that the same effort produced: changes to
generated files are not accepted here, and bug reports are routed to the issue
tracker so the fix can be made upstream in the API definition instead.

## Consequences

**`.fernignore` is load-bearing and easy to forget.** A new hand-maintained file
that is not listed there works fine until the next regeneration, at which point
it silently disappears or reverts. One instance of this is live today:
`tests/custom.test.ts` carries the generator's own comment "Be sure to mark this
file in `.fernignore`", and no `tests/` entry exists in `.fernignore`.

**There is a second, weaker safety net that should not be relied on.** Fern
Replay records hand-made commits as patches in `.fern/replay.lock` and reapplies
them on top of each new generation. Three patches are recorded there today:
`patch-b7675864`, `patch-e3d78ca2`, `patch-d795327b`.

That mechanism works, but it makes generated commit metadata unreliable.
`dd47abf` is the clearest example. Its `[fern-autoversion]` message claims:

> Also broadens the minimum supported Node.js version from 22 to 18 [...]
> Remove `renovate.json` dependency automation config

Neither happened. The same commit reports `[fern-replay] Applied
customizations — Patches applied (2): patch-e3d78ca2, patch-d795327b`, which
restored both. The actual diff to `package.json` in `dd47abf` is a single line —
the placeholder version going from `.5` to `.6`. `engines.node` on `main` is
still `>=22.0.0`, and `renovate.json` is still present (`git log -- renovate.json`
shows only its creation in `e3d78ca`).

**`changelog.md` inherited that error and is currently wrong.** Its
`0.0.0-fern-placeholder.6` entry records "Minimum Node.js version lowered from
`>=22.0.0` to `>=18.0.0`", which contradicts `package.json`, the `setup-node`
step in `publish.yml`, and the runtime-compatibility list in `README.md` — all
of which say Node 22.

**Practical rule that follows:** trust the working tree over generated commit
messages and over `changelog.md`. When a regeneration PR claims to have changed
something outside the generated API surface, verify it against the actual diff.
